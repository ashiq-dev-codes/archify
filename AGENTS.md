# Agent Instructions

Rules for any coding agent working in this repo. User docs are in [README.md](README.md) and [CHANGELOG.md](CHANGELOG.md); this file links to them instead of repeating them.

## What this is

`archify` is a Dart CLI on pub.dev. Users run `dart run archify <command>` inside their own Flutter app, and it writes folders and files into that app based on their `archify.yaml`.

Its public API is what users type and keep: commands, flags, the `archify.yaml` format, and the files each preset generates. `lib/archify.dart` exports exist only for `bin/` and the tests.

## Super rules

These two come before everything else. If a task can't be done without breaking one, stop and ask.

1. **Work on every platform.**
   - The CLI runs on every OS developers use: macOS, Windows and Linux. Use only cross-platform `dart:io` APIs; no shell commands, OS checks or hard-coded line endings.
   - Generated code builds on every platform Flutter supports, web included. Templates must not import `dart:io`, `dart:html` or other platform-only libraries, or suggest packages that skip a platform.
   - Never remove a platform from `platforms:` in [pubspec.yaml](pubspec.yaml).
2. **Stay lightweight.** archify installs into users' apps, so everything it adds costs them.
   - Use the Dart SDK before a package. Ask before adding any `dependencies:` entry; `dev_dependencies` don't reach users.
   - Keep the published package small: anything users don't need goes in [.pubignore](.pubignore).
   - Generated code needs only the Flutter SDK. A template that needs a package is opt-in, and the CLI prints the `flutter pub add` command for it.
   - Keep the CLI fast and offline: no network calls, no spawning other processes.

## Golden rules

1. **Never lose a user's code.** See [Writing into a user's project](#writing-into-a-users-project).
2. **The CLI is public.** Renaming a command or flag, changing an `archify.yaml` key or its meaning, or changing a preset's output is a breaking change. List it under **Breaking changes** in the CHANGELOG.
3. **Copy the nearest existing example** of a command, preset or template.
4. **Change only what the task needs.** No drive-by refactors, renames or reformatting.
5. **Don't guess.** If a requirement or a preset's intended layout is unclear, ask.

## Writing into a user's project

- Create files and folders with `createFile` and `createFolder` in [fs_utils.dart](lib/src/utils/fs_utils.dart). `createFile` **replaces** a file whose content differs, so use it only for files archify generated, never for a file the user may have written.
- Record every generated path in `.archify/manifest.json` ([manifest.dart](lib/src/utils/manifest.dart)). When a path drops out of `archify.yaml`, [reconcile.dart](lib/src/utils/reconcile.dart) moves it to `.archify/removed/<timestamp>/` instead of deleting it. New file-generating code must do the same.
- Before replacing or removing anything the user may have edited, ask first and keep a backup. `configure` (for `lib/main.dart`), `custom` and `reset-project` show the pattern.
- Never edit the user's `pubspec.yaml`. Print the `flutter pub add` command instead.
- Build paths as project-relative strings joined with `/`.

## Output, prompts and errors

- Print with `print` and the existing prefixes: ✅ done, ⚠️ warning, ❌ error. Prompts use `stdout.write`.
- Every prompt has a default, used on empty input or closed stdin. The default must be the answer that keeps the user's code.
- Throw `Exception('...')` with a message the user can act on. Commands catch it and print it.

## Before you finish

There is no CI. Run all three and make them pass:

```sh
dart format --output=none --set-exit-if-changed lib bin test
dart analyze lib bin test   # not the whole repo: example/ needs Flutter
dart test
```

Then check:

- Both [super rules](#super-rules) still hold: nothing platform-only and no new weight.
- Every new command, flag or preset has a test.
- The README covers every user-visible change, and the CHANGELOG lists it (breaking changes called out).
- You followed the `AGENTS.md` of every folder you changed.

## Releasing

- The version lives in `pubspec.yaml` and in `packageVersion` in [version_utils.dart](lib/src/utils/version_utils.dart). Change both together.
- Add a CHANGELOG entry at the top in the existing format: `## <version>`, bold sub-heads and `*` bullets.
- `dart pub publish --dry-run` must pass without warnings. Only publish when asked.

## Code style and commits

- Match the file you're in. `dart format` decides formatting.
- Comments explain *why*, not *what*: lines under 100 characters, blocks under 4 lines. No commented-out or unused code.
- Commits follow Conventional Commits like the history: `feat:`, `fix:`, `refactor:`, `docs:` or `chore:` plus a summary. Only commit when asked.

## Keeping these files current

- `AGENTS.md` is the only instruction file. Don't add a `CLAUDE.md` or other tool-specific copies.
- Each rule lives in one place: here if it applies everywhere, otherwise in the folder where someone would break it.
- Give a folder its own `AGENTS.md` only when it has several rules nothing else needs, and add it to the table above.
- Point to the file that holds a value (version, preset list, template list) instead of copying the value.
- If you find a rule that's out of date, fix it in the same change.
