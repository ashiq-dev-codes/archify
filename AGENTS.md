# Agent Instructions

Rules for any coding agent (Claude Code, Cursor, Codex, Copilot, ...) working in this repo. Read this before touching code.

User docs live in [README.md](README.md) (commands, presets, `archify.yaml`) and [CHANGELOG.md](CHANGELOG.md). This file links to them instead of repeating them.

## What this package is

`archify` is a Dart CLI, published on pub.dev, that scaffolds a Flutter project's folder structure. Users run it inside their own app (`dart run archify <command>`). It reads their `archify.yaml` and writes folders and files into their project.

Its public API is what users type and keep in their repos: the commands and flags, the `archify.yaml` format, and the files each preset generates. The exports in `lib/archify.dart` exist for `bin/` and the tests only.

## Golden rules

1. **Never lose a user's code.** archify writes into other people's projects. A change must never delete or silently overwrite a file the user may have edited (see [Writing into a user's project](#writing-into-a-users-project)).
2. **Treat the CLI as public.** Renaming a command or flag, changing `archify.yaml` keys or their meaning, or changing what a preset generates is a breaking change. Say so clearly and list it under **Breaking changes** in the CHANGELOG.
3. **Keep dependencies minimal.** archify is installed into users' apps, so every dependency can clash with theirs. Ask before adding one.
4. **Follow the existing pattern.** Copy how a similar command, preset or template is built.
5. **Change only what the task needs.** No drive-by refactors, renames or reformatting of unrelated code.
6. **Don't guess.** If a requirement or a preset's intended layout is unclear, ask.

## Folder rules

This file has the rules for the whole repo. These folders have their own `AGENTS.md` with rules that only matter there:

| File | Covers |
| --- | --- |
| [lib/src/commands/AGENTS.md](lib/src/commands/AGENTS.md) | Commands, architecture presets, templates |
| [example/AGENTS.md](example/AGENTS.md) | The example app archify generated |

Claude Code loads a folder's file when it reads a file in that folder. Other tools may not, so read it yourself before working there.

Keeping these files useful:

- Don't add a `CLAUDE.md` anywhere. Claude Code reads `AGENTS.md` directly, and a `CLAUDE.md` in the same or a parent folder stops it from doing so.
- Each rule lives in one file only: here if it applies everywhere, or in the folder where someone would break it.
- Add a folder file only when a folder has several rules nothing outside it needs, and list it above. A single rule goes in the closest existing file.
- Don't copy values that live in code (versions, preset or template lists). Name the file that holds them, so the rule never goes stale.
- If a rule is out of date, fix it in the same change.

## Project layout

```text

lib/src/
├── archify_cli.dart      # command dispatch and help text
├── commands/<command>/   # one folder per command (see lib/src/commands/AGENTS.md)
└── utils/                # file writing, manifest, reconcile, YAML tree, version
test/archify_test.dart    # runs the real CLI in temp folders
example/                  # a Flutter app generated by archify (see example/AGENTS.md)
```

## Writing into a user's project

- Write through `createFile` and `createFolder` in [fs_utils.dart](lib/src/utils/fs_utils.dart), never with `File(...).writeAsString` directly.
- Record generated paths in `.archify/manifest.json` ([manifest.dart](lib/src/utils/manifest.dart)). When a path drops out of `archify.yaml`, [reconcile.dart](lib/src/utils/reconcile.dart) moves it to `.archify/removed/<timestamp>/` instead of deleting it. New file-generating code must do the same.
- Before replacing a file that may hold user content, back it up or ask first, like `configure` does with `lib/main.dart`.
- archify never edits the user's `pubspec.yaml`; it prints the `flutter pub add` command instead. Keep it that way.
- Build paths with `/` and project-relative strings, like the existing code.

## Output and errors

- Print with `print`, using the existing prefixes (✅ done, ⚠️ warning, ❌ error). Prompts use `stdout.write`.
- Every prompt needs a default answer, used when stdin is closed. The tests depend on this.
- Throw `Exception('...')` with a message the user can act on; commands catch and print it.

## Run, check, test

There is no CI, so run these before you finish:

- `dart format --output=none --set-exit-if-changed lib bin test`
- `dart analyze lib bin test` (a whole-repo `dart analyze` also checks `example/`, which needs Flutter)
- `dart test`: the tests run `dart bin/archify.dart` in a temp folder. Add a test for every new command, flag or preset.

## Releasing

- The version lives in two places: `pubspec.yaml` and `packageVersion` in [version_utils.dart](lib/src/utils/version_utils.dart). Change both together.
- Add a CHANGELOG entry at the top in the existing format: `## <version>`, bold sub-heads (with **Breaking changes** when there are any) and `*` bullets.
- Update the README for any user-visible change to commands, flags, presets or `archify.yaml`.
- `dart pub publish --dry-run` must pass without warnings. Only publish when asked.

## Code style

- Match the file you're in: naming, structure and `dart format` formatting.
- Comments explain *why*, never *what*. Keep each comment line under 100 characters and each comment block under 4 lines.
- Don't leave commented-out code or unused code behind.

## Commits

- Use Conventional Commits, like the existing history: `type: summary`, e.g. `feat: add mvvm preset` or `fix: keep user edits on configure`. Types are `feat`, `fix`, `refactor`, `docs` and `chore`.
- Only commit when asked.

## Before you finish

- No path loses or silently overwrites a file the user edited.
- `dart format`, `dart analyze lib bin test` and `dart test` pass.
- The README and CHANGELOG cover every user-visible change, and breaking changes are called out.
- If you bumped the version, it matches in both places.
- You followed the folder `AGENTS.md` for every folder you changed.
